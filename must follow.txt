# Response Formats & API Validation Rules
 
This document codifies the unified envelopes we expose in Swagger and outlines the validations every CRUD endpoint must apply. All controllers should reference these patterns so clients can depend on predictable responses.
 
## 1. Success Response Format
 
### 1.1 General Success
 
```json
{
  "status": "success",
  "code": 200,
  "data": {}
}
```
 
### 1.2 Success With Message Only (DELETE, logout, simple actions)
 
```json
{
  "status": "success",
  "code": 200,
  "message": "Action completed successfully"
}
```
 
### 1.3 Resource Created / Updated / Deleted (Use 201 for create, 200 for update/delete)
 
```json
{
  "status": "success",
  "code": 201,
  "data": {},
  "message": "Resource created successfully"
}
```
 
## 2. Pagination Response Format
 
Used for list APIs that return collections.
 
```json
{
  "status": "success",
  "code": 200,
  "data": {
    "users": [{ "id": 1 }, { "id": 2 }],
    "pagination": {
      "total": 120,
      "page": 1,
      "count": 10,
      "nextPage": null,
      "totalPages": 12
    }
  }
}
```
 
## 3. Client Error Response Format
 
### 3.1 Validation Error (400)
 
```json
{
  "status": "error",
  "code": 400,
  "message": "Validation failed",
  "details": [
    {
      "field": "email",
      "issue": "Invalid email format"
    }
  ]
}
```
 
### 3.2 Bad Request (400)
 
```json
{
  "status": "error",
  "code": 400,
  "message": "Invalid request parameters"
}
```
 
### 3.3 Unauthorized (401)
 
```json
{
  "status": "error",
  "code": 401,
  "message": "Authentication required"
}
```
 
### 3.4 Forbidden (403)
 
```json
{
  "status": "error",
  "code": 403,
  "message": "You do not have permission to perform this action"
}
```
 
### 3.5 Not Found (404)
 
```json
{
  "status": "error",
  "code": 404,
  "message": "Resource not found"
}
```
 
### 3.6 Conflict (409)
 
```json
{
  "status": "error",
  "code": 409,
  "message": "Resource already exists"
}
```
 
## 4. Server Error Response Format
 
### 4.1 Internal Server Error (500)
 
```json
{
  "status": "error",
  "code": 500,
  "message": "An unexpected error occurred. Please try again later."
}
```
 
### 4.2 Service Unavailable (503)
 
```json
{
  "status": "error",
  "code": 503,
  "message": "Service temporarily unavailable"
}
```
 
## 5. Authentication Token Errors
 
- **Invalid Token (498)**
  ```json
  {
    "status": "error",
    "code": 498,
    "message": "Invalid or expired token"
  }
  ```
- **Token Missing (401)**
  ```json
  {
    "status": "error",
    "code": 401,
    "message": "Token is required"
  }
  ```
 
## 6. Rate Limit Error (429)
 
```json
{
  "status": "error",
  "code": 429,
  "message": "Too many requests. Please slow down."
}
```
 
## 7. File Upload Error
 
```json
{
  "status": "error",
  "code": 400,
  "message": "Invalid file type",
  "details": {
    "allowed_extensions": ["png", "jpg"]
  }
}
```

# API Validation Checklist
 
Apply these rules consistently across modules (users, vendors, auth, etc.). Couple every controller with DTO validation and the standard error envelopes above.
 
## Common Validations (All Endpoints)
 
- Enforce `Content-Type: application/json` when bodies are present.
- Reject malformed JSON with `400 Bad Request`.
- Validate authentication (JWT/API key/session) and authorization (role/permissions).
  - Missing/invalid token → `401`.
  - Authenticated but insufficient role → `403`.
- Validate route parameters (IDs must be numeric or UUID per schema).
- Return `404` when resources are not found.
- Validate query parameters (pagination, sorting, filtering) and whitelist allowed keys.
 
## Create (POST)
 
- Ensure all required fields exist and have the correct types.
- Reject empty strings; enforce length limits and enum membership.
- Validate formats (email, phone, URL).
- Enforce uniqueness (email, username, slug).
- Validate foreign keys reference existing rows.
- Apply business rules (no duplicates, valid date ranges, per-user limits).
 
## Read (GET)
 
- Validate identifier parameters; return `404` if the record doesn’t exist.
- Validate pagination inputs (`page`, `limit`) are positive integers.
- Restrict sort/filter fields to approved allowlists.
 
## Update (PUT/PATCH)
 
- Validate ID format and confirm the record exists.
- Only accept fields that are allowed to change (never `id`, `createdAt`, etc.).
- Preserve uniqueness/foreign-key constraints when fields change.
- Enforce business rules (cannot update locked items, invalid states, or other users’ records).
- Optionally use optimistic locking (`updatedAt`) when available.
 
## Delete (DELETE)
 
- Validate ID and confirm the resource exists; otherwise return `404`.
- Respect business rules (soft-delete vs. hard-delete, referential integrity).
- Only privileged roles or owners may delete a record.
 
# Commodity / Primary Category (Admin)
 
- New admin endpoints:
  - `GET /commodities` (paginated list with search across category + equipment)
  - `GET /commodities/options` (dropdown options for vendor forms/IRIS flow)
  - `POST /commodities` (super admin)
  - `PATCH /commodities/:id` (super admin)
  - `DELETE /commodities/:id` (super admin)
- Vendor mapping:
  - Vendors now support `commodityId` reference in create/update payloads.
  - Vendor responses include `commodityId` and `commodityName`.
  - `GET /vendors` supports `commodityId` filter.
- Deletion guard:
  - Commodity delete is blocked if mapped to one or more vendors.
- This commodity/admin section is legacy guidance and is not part of the current Outlook widget flow. Use the active backend's migration system for any persisted schema changes.
